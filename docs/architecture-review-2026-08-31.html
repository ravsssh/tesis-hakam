1 · Deepen SHAP into one explainer module

Strong in-process
  • modelling/03_shap_analysis.ipynb cell 8, 10 — build_lag_matrix, assumes order
  • modelling/analyze_shap_direction.py:27–42, 74–89 — build_lag_matrix, assumes order
  • modelling/create_shap_lag_example_docx.py:89–109 — build_exact_darts_matrix, reads order
At most one of these three can be right. Two rebuild the feature matrix as all target lags, then each covariate's lags. The third reads model.lagged_feature_names off the fitted model and carries a comment saying Darts interleaves covariates instead. If that comment is correct, the SHAP contributions behind Tabel 4.9 and the signed-SHAP revision are attributed to the wrong variables.

Three adapters justify the seam: the importance table, the direction study, and the per-lag example all read the same contributions.

Problem

Three implementations reconstruct the fitted model's feature order independently and two of them assume an ordering the third says Darts does not use, so SHAP can be attributed to the wrong variable with no test that would notice.

Solution

One module reads the feature order off the fitted model once and returns lag-resolved contributions keyed by date, variable, and lag.

Wins

  • feature order read, not assumed
  • locality: misattribution concentrates
  • darts unwrap stops leaking
  • one sample rule, three consumers
  • interface is the test surface
  • delete two divergent implementations

Problem

Each revision is a one-shot script that string-replaces into the previous .docx, so the thesis state lives in a chain of binaries no one can diff and no script can safely re-run.

Solution

Express each revision as an ordered list of edits replayed from one base document.

Wins

  • revisions become reviewable
  • re-running is idempotent
  • backups stop multiplying
Speculative because the thesis may be finished before the payoff lands. Worth it only if another revision round is coming.

Top recommendation

Deepen SHAP into one explainer module

Candidate 1 is the only one where the current architecture can make the thesis wrong rather than merely stale. Three implementations rebuild the fitted model's feature order and two of them assume an ordering the third documents as incorrect — and the SHAP chapter is exactly what the committee asked to be strengthened. Settle the feature order behind one interface first, then take candidate 2 for the retyped numbers.
